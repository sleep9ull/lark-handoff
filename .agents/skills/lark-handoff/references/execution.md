# 开发与合并

每条路径开始前都读取 [audit.md](audit.md)。以当前远端、任务内容和审计为依据恢复，不能仅凭“上次运行失败”重做 Git 操作。

## ready-for-agent

1. **核对交接。** 确认分组对应仓库、任务要求、验收标准和前置依赖。读取项目指令、Git 状态、现有任务分支及工作树。比较任务描述和新增人类评论与上次记录，确认返工范围。完成标志是能说明具体要改什么、如何判断完成。
2. **建立执行现场。** Fetch 既有 `origin`，从最新 `origin/main` 创建任务分支与隔离 worktree；恢复时沿用原任务分支，并核对未提交内容归属。保留用户本地改动，不 stash、reset、clean 用户工作区。将开始记录写入本地 journal 并评论到任务；评论不可写则停止开发并报告。
3. **实现并验证。** 做满足验收标准的最小改动；按目标项目要求运行相关验证。错误修复应有能复现问题的检查。仅文档或低影响修改采用相应检查即可。记录命令、退出结果、未覆盖项以及有证据支持的不确定性。
4. **交付提交。** 检查 diff、敏感文件和变更范围，只提交本任务改动。按 `feature(scope): description` 等类型标题、正文 `- ` 条目的格式提交。推送任务分支到已验证的 `origin` 并回读远端 SHA；不 force push。存在应跑未跑的检查、测试失败、需求关键歧义或无法交付时，保存可审阅成果并进入 `need-to-refine`，不能宣称完成。
5. **记录并交接。** 正常完成时写 `ready-to-review` 交付评论，包含完整 HEAD SHA、分支、diff/PR 链接（若已有）、验收步骤和验证证据。按审计顺序更新状态并回读。无需每个任务创建 PR；目标仓库要求 PR 时按仓库流程执行。

如果任务已由现有代码满足，记录证明和现有 commit，而非制造空提交。将“无代码改动”作为需人类判断的交付，进入 `need-to-refine`。

置信度用具体证据描述：哪些标准已验证，哪些缺少环境、权限或结论。不用无依据的数字百分比。

## ready-to-merge

1. **确定验收对象。** 从最近有效的交付评论取得仓库、任务分支和完整 `review_head`。人类将状态改为 `ready-to-merge` 表示批准该次交付的 SHA；任务新增的范围变化需重新验收。只有状态、没有交付记录或具体提交时，记录问题并进入 `need-to-refine`。
2. **检查重复执行。** Fetch 远端并读取本地 journal。若有记录的合并结果，确认 `review_head` 已在 `origin/main` 历史中，走恢复回写；已经合并却评论或状态失败时，不再次合并。
3. **核对批准仍然有效。** 核对任务分支当前本地和远端 HEAD 都等于 `review_head`，且工作树干净。分支多了新提交或存在未提交改动时，保留现场、进入 `need-to-refine`，不能把新内容夹带进已批准的合并。检查当前任务仍为 `ready-to-merge`。
4. **形成合并结果。** 使用基于最新 `origin/main` 的干净临时整合 worktree，合并精确的 `review_head`，保留任务提交历史。不要 rebase/squash 改写验收 SHA。运行项目要求的合并后检查；若有冲突，停止合并、保留错误证据并进入 `need-to-refine`，由人类决定返工，不能自行解决后直接发布未经验收的改动。
5. **发布并验证。** 推送前再次读取任务状态，并确认人类未撤回授权。普通非强推将整合结果推送至 `origin/main`；推送后 Fetch，使用 `git merge-base --is-ancestor <review_head> origin/main` 及远端引用验证成果已到达。只有成功证据齐全时才记录合并 SHA 并更新为 `merged`。

如果目标仓库要求 PR、必需 CI 或保护分支，按既有流程合并同一个已验收 SHA，不绕过保护或变更仓库设置。仅支持 squash/rebase 的仓库需要先明确其验收 SHA 到合并 SHA 的核验方式；默认路径不声称能用祖先检查验证被改写的提交。

远端 `main` 竞争导致非快进拒绝时，重新 Fetch、重新整合与验证一次；再次发生则保留证据并进入 `need-to-refine`，避免无限重试。推送响应不确定时先读取远端事实再决定，不把传输超时直接视为失败。

## 途中变化与失败

- 人类将任务移出触发状态、移出清单或修改关键范围：停止新的开发/合并动作，保留本任务分支，评论当前进展；不覆盖人类的新状态。
- 已合并之后发现状态被人类改动：只评论已发生的远端事实，不强行改回 `merged`。
- 单任务的代码或配置问题：记录证据和具体待人工解决事项，状态仍为预期触发状态且可写时转入 `need-to-refine`，然后可继续其他任务。
- 全局身份、权限或状态配置不完整：停止本轮执行，不尝试用别名、bot 身份或其他接口绕过；保留一次运行错误，向用户指出缺失项。
- 外部环境暂时不可用：保存现场和失败原因；同一阻塞在未发生变化时不反复发表评论，恢复依据见审计文档。

Git 操作和任务 API 均不保证跨系统事务，也无法彻底消除“刚读完状态就被人类修改”的竞争窗口。单写入者、关键动作前复读和可恢复审计用于缩小这一窗口；发生冲突时以实际 Git 结果和最新人类状态分别记录。

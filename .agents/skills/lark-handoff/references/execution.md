# 开发与合并

sub-agent 只执行主 Agent 分配的一个飞书任务；先读取 [dispatch.md](dispatch.md) 的执行边界和 [audit.md](audit.md)。以当前远端、任务内容和审计为依据恢复，不能仅凭“上次运行失败”重做 Git 操作。

## ready-for-agent

1. **核对交接。** 复读「所属项目」，确认其对应仓库与派发记录一致、任务要求、验收标准和前置依赖。读取项目指令、Git 状态、现有任务分支及工作树。比较任务描述和新增人类评论与上次记录，确认返工范围。完成标志是能说明具体要改什么、如何判断完成。
2. **建立执行现场。** Fetch 既有 `origin`，复查主 Agent 预留名称的占用与归属后，从最新 `origin/main` 创建任务分支与隔离 worktree；恢复时沿用原任务分支，并核对未提交内容归属。保留用户本地改动，不 stash、reset、clean 用户工作区。将开始记录写入本地 journal 并评论到任务；评论不可写则停止开发并报告。
3. **实现并验证。** 做满足验收标准的最小改动；按目标项目要求运行相关验证。错误修复应有能复现问题的检查。仅文档或低影响修改采用相应检查即可。记录命令、退出结果、未覆盖项以及有证据支持的不确定性。
4. **交付提交。** 检查 diff、敏感文件和变更范围，只提交本任务改动。按 `feature(scope): description` 等类型标题、正文 `- ` 条目的格式提交。推送任务分支到已验证的 `origin` 并回读远端 SHA；不 force push。存在应跑未跑的检查、测试失败、需求关键歧义或无法交付时，保存可审阅成果并进入 `need-to-refine`，不能宣称完成。
5. **交付 PR 并交接。** 查找同一任务分支已有的 PR，存在则更新，否则创建以 `main` 为目标的 PR；核对目标仓库、base、head 分支与完整 HEAD SHA。PR 描述写明完整飞书任务 GUID、任务链接、行为变化、验证结果和验收步骤。运行并检查项目要求的 CI，必需检查通过后才交付；未配置 CI 时明确记录并以项目要求的本地检查为准。创建 PR 失败、必需 CI 失败或本轮结束仍未完成时，保存分支、PR 和检查证据，进入 `need-to-refine`。正常完成时写 `ready-to-review` 交付评论，包含完整 HEAD SHA、分支、PR 链接、本地 worktree 路径或预览入口、验收步骤和验证证据。按审计顺序更新状态并回读。返工更新同一 PR；任何新提交都需重新交付并由人类验收。

如果任务已由现有代码满足，记录证明和现有 commit，而非制造空提交。将“无代码改动”作为需人类判断的交付，进入 `need-to-refine`。

置信度用具体证据描述：哪些标准已验证，哪些缺少环境、权限或结论。不用无依据的数字百分比。

## ready-to-merge

1. **确定验收对象。** 从最近有效的交付评论取得仓库、任务分支、PR 链接和完整 `review_head`。人类将状态改为 `ready-to-merge` 表示批准该次交付的 SHA；任务新增的范围变化需重新验收。缺少 PR 或具体提交时，记录问题并进入 `need-to-refine`。
2. **检查重复执行。** Fetch 远端并读取本地 journal 与 PR 状态。PR 已合并时，核实合并证据和远端结果后走恢复回写；结果无法核实则进入 `need-to-refine`。已经合并却评论或状态失败时，不再次合并。
3. **核对批准仍然有效。** 复读「所属项目」并核对其对应仓库与交付记录一致；核对 PR 的目标仓库和 base 为该项目 `main`，head 分支、本地与远端 HEAD 均等于 `review_head`，且工作树干净、任务仍为 `ready-to-merge`。分支多了新提交、存在未提交改动或 PR 已关闭未合并时，保留现场并进入 `need-to-refine`。核对必需 CI、评审和分支规则均满足；不得用飞书批准绕过仓库要求。
4. **验证合并。** 默认使用保留任务提交历史的 merge commit。需要本地合并后检查时，在最新 `origin/main` 的干净临时整合 worktree 合并精确的 `review_head` 并运行检查，此工作树只用于验证，最终通过 PR 合并。冲突或检查失败时记录证据并进入 `need-to-refine`；修复产生的新提交必须重新交付验收。仅支持 squash/rebase 的仓库须先明确验收 SHA 到合并 SHA 的核验方式；未明确时进入 `need-to-refine`，不更改仓库设置。
5. **合并并确认完成。** 合并前再次读取任务状态与关键内容、PR HEAD 和必需检查。通过平台 PR 合并接口执行，并使用预期 HEAD 条件保护（若工具支持）；不启用稍后自动合并，避免人类撤回授权后仍合并。若平台无法保证合并的是批准 SHA，停止并报告。合并后 Fetch，核对 PR 的已合并状态、合并 SHA，并用 `git merge-base --is-ancestor <review_head> origin/main` 及远端引用验证成果已到达；改写提交的策略使用事先明确的对应核验方式。证据齐全后评论合并结果并更新为 `done`，无需人类再确认一次。

合并时远端 `main` 变化导致拒绝，重新读取 PR 和远端并验证一次；再次失败则进入 `need-to-refine`，避免无限重试。CI 或评审尚未完成时保存缺失条件并进入 `need-to-refine`。合并响应不确定时先读取 PR 和远端事实再决定，不把传输超时直接视为失败。PR 合并及必需检查按当前平台工具文档执行，不通过直接推送 `main` 绕过 PR 流程。

## 途中变化与失败

- 人类将任务移出触发状态、移出清单、修改「所属项目」或关键范围：停止新的开发/合并动作，保留本任务分支，评论当前进展；不覆盖人类的新状态。
- 已合并之后发现状态被人类改动：只评论已发生的远端事实，不强行改回 `done`。
- 单任务的代码或配置问题：记录证据和具体待人工解决事项，状态仍为预期触发状态且可写时转入 `need-to-refine`，然后可继续其他任务。
- 全局身份、权限或状态配置不完整：sub-agent 保存现场并立即通知主 Agent；主 Agent 停止派发并通知其他执行者停止新动作，按调度规则收尾本轮，不尝试用别名、bot 身份或其他接口绕过；保留一次运行错误，向用户指出缺失项。
- 外部环境暂时不可用：保存现场和失败原因；同一阻塞在未发生变化时不反复发表评论，恢复依据见审计文档。

Git 操作和任务 API 均不保证跨系统事务，也无法彻底消除“刚读完状态就被人类修改”的竞争窗口。每项任务的单写入者、关键动作前复读和可恢复审计用于缩小这一窗口；发生冲突时以实际 Git 结果和最新人类状态分别记录。

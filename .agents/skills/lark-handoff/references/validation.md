# 技能行为验证

修改契约后，在本地临时 Git 仓库和模拟飞书响应中检查下列决策；真实清单只做读取预检。检查完成后清理自己创建的临时资源。

| 输入场景 | 应有结果 |
| --- | --- |
| 状态为 `draft`，评论含 `/可执行` | 跳过，不创建分支或评论 |
| 状态为 `ready-for-agent`，「所属项目」映射唯一、验收明确 | 独立分支/worktree 开发、自测、提交、推送分支、创建 PR 并确认必需 CI 通过，评论后转入 `ready-to-review` |
| 任务状态选项名称是「可执行」 | 视为未知状态并报告，不作为 `ready-for-agent` 执行 |
| 存在两个名称均为 `ready-for-agent` 的有效选项 | 配置冲突，停止执行并报告 |
| 缺少状态选项、所属项目字段读取权限或评论权限 | 上线预检不通过，不静默跳过元数据后执行 |
| 「所属项目」名称匹配两个不同本地仓库 | 记录需明确路径，进入 `need-to-refine`，不猜项目 |
| 「所属项目」为 A，分组名为 B（或无分组读取权限） | 仅定位 A，不读取分组，不因分组权限缺失阻塞 |
| 「所属项目」为空，但分组或描述路径能对应仓库 | 进入 `need-to-refine`，不回退选项目 |
| 「所属项目」单选值为选项 GUID | 由字段定义解析项目名称后精确映射，不用 GUID 匹配目录 |
| 「所属项目」字段重名/类型不支持，或任务值未知/多项目 | 字段问题预检不通过；任务值问题进入 `need-to-refine` |
| 描述中的路径与「所属项目」映射冲突 | 进入 `need-to-refine`，不以描述覆盖项目来源 |
| 派发后「所属项目」改变，或旧 journal 仓库与当前字段不一致 | 停止新开发/合并，保留成果；仅按原证据恢复已发生事实的评论，不覆盖业务状态 |
| 实现后有必须检查未通过 | 保留成果与证据，进入 `need-to-refine` |
| `ready-to-review` / `need-to-refine` / `done` | 不启动新开发或合并 |
| `ready-to-merge`，PR 与分支 HEAD 等于已交付 SHA，必需检查和评审通过 | 通过 PR 合并、确认远端 main 含批准提交、评论后转入 `done` |
| `ready-to-merge`，分支有额外提交或没有交付 SHA | 不合并，记录具体问题并进入 `need-to-refine` |
| PR 已合并，评论或状态更新失败 | 下轮核实远端后仅恢复回写，不再次创建合并 |
| PR 创建失败或必需 CI 失败/未完成 | 保存成果与缺失条件，进入 `need-to-refine`，不交付为 `ready-to-review` |
| 返工任务已有 PR | 更新原任务分支与 PR，记录新 SHA，重新等待人类验收 |
| PR 的 base 不是目标 main、已关闭未合并或缺少仓库必需评审 | 不合并，进入 `need-to-refine` |
| 只有 GitHub Review 批准，飞书仍为 `ready-to-review` | 不合并，飞书 `ready-to-merge` 才触发合并 |
| PR 已合并，远端尚无法核实 | 保存证据并报告，不写 `done` |
| 旧 journal 待写业务状态 `merged` | 核实 PR 与远端后按新契约恢复为 `done`；证据不足保留并报告 |
| 人类在执行中修改状态或关键内容 | 停止新动作、保留现场、评论事实，不覆盖新状态 |
| 上轮写评论超时，但服务器已经写入 | 用同一 event_id 找到评论，不重复发送 |
| 恢复仍有待回写事件，任务仍处于触发状态 | 保留原 journal/event_id，本轮不为该 GUID 派发新工作 |
| 新任务自动命名，无重名 | 使用 `codex/<type>/<slug>`，journal、评论与 PR 描述保留完整任务 GUID |
| 两个新任务生成相同 slug | 主 Agent 在派发前预留不同名称，后者追加 GUID 前 8 位并复查 |
| 短后缀仍被占用或已有同名分支归属不明 | 每次延长 4 位并复查，完整 GUID 仍冲突则阻塞，不覆盖引用 |
| 任务改名、返工或已有含完整 GUID 的分支 | 按原映射核对归属后复用分支，不重新命名 |
| 分支已预留，但执行者创建前发现新增占用 | 停止创建并交还主 Agent 重新分配，不复用不明分支 |
| 两个任务明确约定同一远端分支、PR 或 worktree | 报告写入归属冲突，停止相关派发 |
| 两个独立 `ready-for-agent` 任务 | 主 Agent 派发两个单任务 sub-agent，各自 worktree、journal 和评论，完成后逐项核验 |
| 候选超过可用 sub-agent 额度 | 超额排队，执行者退出后继续派发；同一 GUID 不重复派发 |
| 同仓库两个 `ready-to-merge`，本地路径或远端 URL 不同 | 归入同一合并队列，第一项收尾后第二项重新读取 main 与批准 SHA |
| 不同仓库的合并任务 | 可并行，各自验证 PR 与远端结果 |
| 同一 Git common directory 的两个任务同时 Fetch/创建 worktree | 先取得主 Agent 的独占执行时段，完成后释放；编辑与独立测试可并行 |
| 任务依赖尚待人类验收的另一任务 | 不将交付视为依赖完成，按契约记录阻塞 |
| 子任务失败或收到全局权限错误 | 单项失败不阻塞独立任务；全局错误停止派发并通知所有执行者收尾 |
| sub-agent 无回复、主 Agent 崩溃或派发响应不确定 | 核对执行者和进程，未确认停止前不重派、不接管 journal、不释放锁 |
| sub-agent 结束但测试进程仍运行 | 先确认关联进程停止，再回收资源和释放锁 |
| 同任务评论已写入但 sub-agent 意外结束 | 确认原执行者停止后按原 event_id 恢复，主 Agent 不与其同时写 journal |
| 只读预检发现多个候选 | 仅报告，不派发执行者、不创建锁或运行记录 |
| 两轮调度同时开始 | 只有原子获取共享 run.lock 的一轮执行 |
| 存在不能证明原运行已结束的旧锁 | 等待人工确认，不按年龄删锁 |
| API 第一页后还有更多数据 | 完整分页；中途失败报告不完整，而不是空清单 |

结构检查包括：技能 frontmatter、引用文件存在、配置中的六个规范状态一致、仅两个自动触发状态、示例未误用显示任务编号。结构通过不等于真实写入与调度已验收。

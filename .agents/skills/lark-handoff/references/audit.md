# 评论审计与重入恢复

## 本机运行锁

Scheduled 的多次运行可能重叠。默认同一清单只在一台主机、一个 Codex 调度入口执行，不新增业务状态 `in-progress`。

固定运行目录为 `~/.local/state/lark-handoff/<tasklist-guid>/`，通过用户主目录展开成绝对路径；不同调度工作树必须共享该目录。目录只保存运行元数据、锁、journal 和隔离 worktree，不保存登录 token。

执行模式用原子的目录创建取得 `run.lock`，写入 `owner.json`：`run_id`、主机名、Codex 任务/运行标识（可用时）、开始时间。只有创建成功者能运行；已有锁时结束本轮，不先删锁再执行。锁覆盖扫描后所有副作用、状态回写及 Git 推送，顺序处理任务。

正常结束移除自己持有的锁。崩溃遗留锁只能在确认原 Codex 运行已结束、没有关联 Git/测试进程仍运行后恢复；不能仅靠锁的年龄判断，也不能用短命 shell PID 当作整个 Codex 运行的存活证明。无法确认时要求人工处理。多主机部署需另行实现共享互斥，单机锁不能保证跨主机排他。

## 任务 journal

每次接管生成 `run_id`，每项任务在运行目录保存 `<task-guid>.json`。使用临时文件加原子替换持久化，每次 Git 或飞书副作用前写意图，成功后写证据。

必要字段：

- 身份：清单 GUID、任务 GUID、run_id、Codex 运行标识、更新时间（带时区）。
- 输入：开始时状态/选项 GUID、任务描述摘要或 hash、已读取评论 ID、项目真实路径、分组 GUID。
- Git：工作树、分支、base SHA、PR 链接与编号、交付 `review_head`、CI/评审证据、整合/合并 SHA、远端推送及 PR 合并确认。
- 进度：当前步骤、待发评论原文与 `event_id`、目标状态、已确认评论 ID、状态回读结果、阻塞原因。

journal 是恢复线索，飞书最新状态与 Git 远端事实仍需重新读取。丢失 journal 时可从已确认的评论恢复分支和交付 SHA；无法确认验收对象则停止合并。

## 评论模板

每次实际接管后，至少有开始和最终结果评论；后续仅在重要里程碑或失败时追加。未触发的任务不评论。每条评论包含可检索的唯一事件标记，发出前先记录原文：

```text
[handoff-log/v1] event_id=<run_id>:<task_guid>:<phase>
动作：开发 / 合并 / 恢复
阶段：started / delivered / blocked / merged / reconciled
时间：<ISO 8601，含时区>
运行：<run_id；可用时附 Codex 任务链接或 ID>
任务：<任务链接>
状态：<观察到的状态> → <计划状态；保持不变时说明>
项目：<真实路径与已验证远端>
分支：<分支名>；基线：<完整 SHA>
PR：<链接或尚未创建>
验收提交：<完整 SHA 或尚未产生>
合并提交：<完整 SHA 或尚未合并>
结果：<实际行为变化、范围或停止原因>
验证：<检查命令、退出结果及必要证据>
未验证与风险：<具体缺口，没有则写无>
人工下一步：<如何验收或需要补充的信息>
```

可省略尚不适用的 Git 字段，交付和合并结果必须含对应完整 SHA。长日志留在可访问的产物中，评论只放摘要与链接；避免把 token、环境密钥或原始用户数据贴入评论。

## 回写顺序和恢复

1. 将真实执行结果、目标状态与最终评论保存至 journal。
2. 读取评论列表，按 `event_id` 判断该事件是否已发送。未发送时才创建评论，并保存返回的评论 ID。超时后先重读评论再重试。
3. 重新读取任务，只有当前状态仍等于本动作开始时的预期触发状态、关键输入未变化时才更新目标状态；已经是目标状态则核验后视为成功。人类已改状态时仅记录事实，不覆盖。
4. 回读状态和评论，核对成功后将 journal 标记为回写完成。评论中的箭头是计划转换，只有回读才证明状态已转换；转换失败时保留待恢复事项。

合并成功但回写失败时，保存 PR 合并证据、已确认的远端 SHA 和目标状态 `done`。下轮在锁内先核对远端，再补发缺失评论和允许的状态更新；即使任务已不是触发状态，也只恢复日志，不触发新的代码操作。

评论没有已验证的幂等键接口，`event_id` 加单写入者用于避免通常的重复发送，不能宣称严格 exactly-once。状态更新同样没有本流程已验证的条件写入能力。重复错误在输入/权限/远端均未变化时只报告一次；后续读取检查恢复条件，恢复后补齐原事件。

旧版本 journal 的目标状态若为 `merged`，恢复时按当前契约核实 PR 与远端合并证据，将目标状态转换为 `done`；证据不足则保留记录并报告，不盲目写入旧状态或宣称完成。历史评论的 `merged` 阶段标记保持不变。
